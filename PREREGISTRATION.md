# PREREGISTRATION: Ray Distributed Lab

Frozen before any measured run. This file is the first content
commit of this repository and precedes every harness and results
file. Any change to this file after the first measured run is an
amendment: it is appended under Amendments with a date and a
reason, never edited silently.

Study: Gap-Closure Programme, Wave 3, item 8. Author of record:
Jesun Ahmad Ushno. Baseline study: pytorch-depth-lab (Batch 4,
Track B4), whose frozen protocol, CPU arms C1 and C2, and
published results this study builds on. That repo is read only
here and is never modified.

## Research question

Against the CPU distributed-training baselines already measured
in pytorch-depth-lab, what does Ray's training and serving stack
cost or buy on the same workload family: scaling efficiency,
accuracy parity, and inference throughput?

## Machine of record (frozen)

- One shared Ubuntu VM, 4 CPU cores (os.cpu_count() = 4),
  7.7 GB RAM, Python 3.12.3, Linux x86_64.
- The core count bounds every scaling claim in this study: the
  largest configuration tested is 2 workers on 4 cores. No claim
  extends beyond this machine.
- Arms run sequentially, one heavy matrix at a time. No other
  study workload runs concurrently by design; the machine is
  shared, so background load from other tenants is a named
  threat, recorded under Threats.

## Pinned versions (frozen)

- torch 2.15.0+cpu, torchvision 0.29.2+cpu (identical to the

- ray 2.60.0 (ray[train] and ray[serve]).

## Frozen recipe (every training arm)

Identical to the baseline study's frozen recipe and its CPU
sub-protocol, except for the subset and the run count:

- Model: torchvision ResNet-18, final layer replaced by
  Linear(512, 10), 11,181,642 parameters, from scratch under
  the run seed.
- Optimizer: AdamW, lr 1e-3, betas (0.9, 0.999),
  weight_decay 1e-4.
- Schedule: CosineAnnealingLR, T_max = 3 epochs.
- Loss: CrossEntropyLoss, no label smoothing.
- Effective batch size 128. Distributed arms use per-rank
  batch 64 at world size 2.
- Epochs: 3. Runs per arm: 3, with seeds 42, 43, 44. The same
  seed set is used by every arm, so runs pair by seed.
- Augmentation (train only): RandomHorizontalFlip(0.5),
  RandomVerticalFlip(0.5). No augmentation at evaluation.
- Normalisation: ImageNet mean (0.485, 0.456, 0.406), std
  (0.229, 0.224, 0.225), all splits.
- Data loading, identical in every arm by design: num_workers
  0, pin_memory False, no persistent workers. The baseline
  study proved this workload data-loading sensitive on its GPU
  arms; here the loader configuration is held fixed so the
  framework comparison is not a loader comparison. This is a
  stated scope limit: a tuned-loader comparison is a different
  study.
- Threads: torch intra-op threads 2 and OMP_NUM_THREADS 2 in
  every training process, mirroring the baseline CPU arms C1
  and C2 exactly. Total thread demand never exceeds the 4
  cores.
- Samplers: the single-process arm shuffles with a generator
  seeded by the run seed. Distributed arms use
  DistributedSampler with the run seed and set_epoch per epoch.
- Time-to-accuracy is NOT registered. With 3 epochs, epoch-end
  readings are too coarse to time a threshold honestly; the
  accuracy endpoint and throughput carry the comparison.

## Baseline context (stated, not hidden)

From pytorch-depth-lab, CPU arms on the same VM class (3
epochs, full 21,600-image train split, seed 42, workers 0):

- C1 single process: epoch wall times 263.6, 265.0, 291.2 s;
  final validation accuracy 0.7600.
- C2 DDP (gloo, world 2): epoch wall times 346.1, 301.5,
  330.3 s; final validation accuracy 0.8559.
- Its H7 failed: per-epoch train losses tracked closely (mean
  absolute difference at most 0.05 nats held), but final
  validation accuracy differed by 9.59 percentage points,
  outside its frozen plus or minus 1.0 pp window. Its GPU arms
  separately showed the workload is data-loading bound (its
  H4): data wait was 53.7 percent of step time before the one
  registered loader fix.
- Consequence for this study: the accuracy-parity hypothesis
  below is written knowing a 9.59 pp divergence already
  happened once under this recipe family. The band is set at
  5.0 pp, wide enough to absorb seed noise at 3 seeds, narrow
  enough that a B4-scale divergence still fails it.

## Training arms (frozen list)

- A: single process. The baseline arm. One process, batch 128,
  threads 2. Mirrors baseline C1 at subset scale.
- B: torch DDP, gloo backend, world size 2, per-rank batch 64,
  DistributedSampler, threads 2 per rank. Mirrors baseline C2
  at subset scale. Rendezvous: file store with a unique file
  per run, and gloo pinned to the loopback interface (both are
  baseline D8 lessons from this VM).
- C: Ray Train, TorchTrainer, 2 workers, resources per worker
  CPU 2, use_gpu False. Model wrapped with
  ray.train.torch.prepare_model; the sampler is a
  DistributedSampler built in the worker with the run seed, so
  the sampler contract is byte-identical to arm B rather than
  whatever a helper would choose. Threads 2 per worker.

## Measurement definitions (frozen)

- Training throughput of a run: total training samples
  processed across all 3 epochs divided by accumulated
  training-step wall time. Step time is measured around the
  forward, loss, backward, and optimizer-step block only.
  Excluded: the first 5 steps of epoch 1 (warmup), sampler and
  loader setup, evaluation, checkpoint saving, and process
  startup. Every rank accumulates the same quantity; arm B and
  C report rank 0's after an agreement check across ranks
  (step counts must match exactly; times may differ, and the
  slower rank's time is the one used, since the epoch ends at
  the barrier).
- Arm throughput: the median of the arm's 3 runs.
- Scaling efficiency of a distributed arm: its median
  throughput divided by (2 times arm A's median throughput).
  Perfect linear scaling is 1.00; the baseline's C2 epoch
  times imply a value below 1.00 on this machine.
- Final test accuracy of a run: accuracy on the full 2,700
  image test split after epoch 3, evaluated in one process
  (rank 0 for distributed arms) at batch 128, workers 0, eval
  transform. Arm accuracy: the mean of the arm's 3 runs;
  per-seed values and per-seed paired differences are reported
  beside it.
- Also logged per run: per-epoch mean train loss, per-epoch
  train wall time, total wall time, environment block.
- Checkpoint for the inference study: the final state_dict of
  arm A, seed 42 (run order A first, so it exists before any
  inference run). Fallback, frozen: if that run fails, arm A
  seed 43. The checkpoint file is not committed (size); its
  SHA-256 is recorded in results/summary.json.

## Inference study (frozen)

- Model: the frozen checkpoint above, eval mode, no gradient.
- Arm P: a plain in-process batched inference loop. One
  process, torch threads 4 (the whole machine), requests
  pulled from a queue and served one batch at a time.
- Arm R: Ray serving. Primary pattern: Ray Serve, 2 replicas,
  2 CPUs per replica, torch threads 2 per replica. Fallback,
  frozen in advance: if a pre-run smoke test, recorded in
  DECISIONS.md before any measured inference run, shows Ray
  Serve cannot start cleanly on this VM, the serving pattern
  is 2 Ray remote actors with the same CPU and thread budget,
  dispatched round-robin, and RESULTS.md names the pattern
  used in its headline table. Either way the total thread
  budget equals arm P's: 4.
- Request stream, identical for both arms: the frozen test
  split in fixed order, cycled. 2 client threads, each sending
  batches in a closed loop (next batch only after the previous
  reply), 5 warmup batches per client (excluded), then 40
  measured batches per client.
- Batch sizes: 128 is the primary cell; 32 is the secondary
  cell. Same stream shape per cell.
- Latency of a batch: client send time to reply receipt,
  including any queue wait in arm P and any framework transit
  in arm R. Reported per cell: pooled p50 and p95 over all
  measured batches.
- Throughput of a cell: total images served divided by the
  makespan from first measured send to last measured receipt.

## Hypotheses and frozen verdict rules

Verdict language: CONFIRMED, REFUTED, INCONCLUSIVE. Verdicts
are computed by scripts/make_results.py from the recorded raw
results under exactly these rules.

- H1 (Ray Train scaling parity with DDP): CONFIRMED if the
  absolute difference between arm C's and arm B's scaling
  efficiencies is at most 0.10. REFUTED if it is above 0.10,
  with the direction stated (Ray more efficient, or Ray less
  efficient, than hand-rolled DDP at world size 2). INCONCLUSIVE
  only if a registered cell is missing.
- H2 (accuracy parity): CONFIRMED if BOTH distributed arms'
  mean final test accuracy sits within plus or minus 5.0
  percentage points of arm A's mean. REFUTED if either arm
  falls outside the band, naming the arm and the signed
  difference. The stated prior risk is the baseline study's
  9.59 pp C2 divergence; no post-hoc band widening is allowed.
- H3 (serving throughput): CONFIRMED if arm R's throughput at
  batch 128 is at least 1.25 times arm P's. REFUTED if the
  ratio is at most 1.00 (the plain loop ties or wins at equal
  thread budget). INCONCLUSIVE if the ratio falls strictly
  between 1.00 and 1.25. The batch 32 cell is reported
  descriptively and carries no verdict.

## Kubeflow assessment (frozen criteria)

KUBEFLOW-ASSESSMENT.md is a written deliverable, not an
install. It judges Kubeflow against exactly these criteria:
(1) install and maintenance weight on a small fleet with no
dedicated platform engineer and no Kubernetes cluster today;
(2) overlap with capabilities this study and pytorch-depth-lab
already prove (DDP, Ray Train, Ray Serve or actors);
(3) what Kubeflow would add that Ray plus DDP do not. Verdict:
one of ADOPT, DEFER, REJECT, with the reasoning shown and the
conditions that would change it named.

## Stop rules (binding)

- S1: if an arm fails to run, the failure and its exact error
  are reported; the arm is not quietly dropped or replaced
  outside the frozen fallbacks.
- S2: if a throughput or accuracy number looks wrong, it is
  recomputed from the raw records before any verdict is drawn;
  no number is hand-adjusted.
- S3: if Ray Serve falls back to actors, the substitution is
  recorded in DECISIONS.md before the measured inference runs
  and named in RESULTS.md.
- S4: no hypothesis band, subset rule, or measurement
  definition in this file changes after the first measured
  run except by a dated amendment below.

## Threats (named in advance)

- Shared-VM background load can move wall times. Mitigations:
  sequential arms, medians over 3 runs, per-epoch times kept
  raw. Residual risk stands and is charged in AUDIT.md.
- Three seeds is a small sample for accuracy. The H2 band and
  the per-seed reporting are the honest response; no interval
  machinery will be used to dress n = 3 as more than it is.
- Workers 0 loading makes every arm pay JPEG decode in the
  training process. This is deliberate (identical across arms)
  and bounds the claim: these are framework overheads measured
  on top of an in-process loader, not on top of a tuned one.

## Claim boundary (frozen)

Results hold for this machine, these pinned versions, this
dataset and recipe only. No claim about multi-node training,
GPUs, NCCL, or clusters larger than 2 workers on 4 cores. No
number is reported without its baseline row, n, seeds, dataset
version, and producing command.
